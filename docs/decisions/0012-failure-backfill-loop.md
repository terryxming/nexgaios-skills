# 0012. 失败回填闭环:真实使用的失败案例自动回流评测(feedback-loop)

- 状态:已接受(通道本身未经真实失败案例走通,试行待验证——见存疑段)
- 日期:2026-07-04
- 决策人:terry(公司机)+ Claude

## 背景

ob-notes v1.0.0 候选整套架构试行待验证(ADR-0011),用户开始真实使用——真实使用必然产生失败案例(呈现侧重误判、确切细节被压、无问存档没引导好、误触发),这些失败正是 skill 迭代的燃料。失败即用例(本 ADR)已规定原则:每个失败先回填成 eval 用例、再改源码。但缺一条**自动化管道**:失败发生在任意会话/任意机器,靠口头记忆带回 dev 仓,必然遗失。

自动化的边界要先划清:**发现失败**是语义判断(A5 桶三性质,机器判不了),**用例审批**被失败即用例(本 ADR)强制人在环("用例运行前必须给用户过目")——这两个人类触点不可消除。自动化的目标是:用户只说一句话,其余环节零摩擦、零遗失。


## 决策

1. **捕获通道住进 ob-notes 自身**(`references/feedback.md`,新规则项 `feedback-loop`):用户在沉淀后指出产出有问题并要求回填时,agent 按其格式把失败现场写成**一个结构化 JSON**——触发语与用户原话**逐字保真**、坏笔记关键段**原样摘录**、疑似违反的规则项与断言草稿由 agent 组织。
2. **config 门控**:`~/.config/ob-notes/config.json` 加可选键 `dev_repo`(本机 dev 仓路径)。配了 = 维护环境,执行捕获;没配 = 普通用户,通道完全惰性。既不在 skill 源写死机器路径(过桶二·1),又让分发出去的同一份 skill 对普通用户无感。
3. **暂存位置在仓内**:`skills/first-party/ob-notes/evals/pending/YYYY-MM-DD-<slug>.json`,一次失败一个文件。捕获**只写这一个文件,不 commit 不 push**——留 dirty 状态,下次维护会话纪律 C「开工」巡检(git 是否 clean)自然看见,dirty 本身就是提醒器,零新增提醒机制。
4. **转换人在环**:维护会话中 agent 读 pending 起草正式 eval 条目 → **用户过目批准**(失败即用例,本 ADR)→ 入 `evals.json`、删暂存、记 dev-log。
5. **发布闸**:`tools/lint.py --release` 新增检查——evals/pending/ 非空即红,未回填不得发布(发布门禁(ADR-0009)前置)。**平时 CI 不查 pending**:否则捕获文件一 push 就红,堵死捕获通道本身。
6. 与 v1.0.0 刚移除的 monitoring 划清界限:monitoring 是**每次沉淀无条件**记 jsonl(常态开销,被否决);本通道是**事件驱动**——仅用户主动报失败时写一条,且仅维护者可见。机制形似,性质不同。


## 证据(附来源,区分已证实/推断)

1. **已证实(库内)**:失败即用例(本 ADR)"线上每个失败案例先回填成一条 eval 用例,再改源码"——本决策是其管道化,原则已有、管道新增。
2. **已证实(库内)**:v1.0.0 移除 monitoring 的理由是"无意义且制造机制负担"(dev-log 决策表 2026-07-03)——第 6 条区别声明的依据。
3. **已证实(库内)**:`tools/lint.py` 桶二可移植检查禁 skill 源含机器路径、但豁免 evals/(评测用例写实机路径属官方建议)——config 门控方案与 pending 落位 evals/ 均与既有门禁兼容。
4. **推断**:dirty 状态作提醒器足够可靠——依赖纪律 C「开工」巡检执行到位;若实践中仍遗失,再考虑纪律 C「开工」清单显式加一条。
5. **推断**:失败频度低到"一次一文件"不成负担;若高频再考虑聚合格式。
